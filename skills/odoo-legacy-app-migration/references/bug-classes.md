# Common Bug Classes Found This Way

Recurring symptom → cause → fix pairs collected across real multi-version
migrations. Scan this table whenever a symptom looks inexplicable; most of
these look like a bug in your own code and are not.

| Symptom | Real Cause | Fix |
|---|---|---|
| Feature works on `/` but nowhere else | Injected via a template/xpath that only applies to a subset of routes (e.g. `portal.frontend_layout`'s `//nav`, which some listing routes don't render through) | Move the injection to a point proven to render on every route (e.g. `web.layout`'s `<head>`) |
| `$ is not defined` (or similar) in the browser console | Inline `<script>` on `DOMContentLoaded` assumes jQuery/a lib is already loaded, but Odoo lazy-loads part of the asset bundle | Rewrite as a `publicWidget` — it only attaches once its declared dependencies are actually loaded |
| A "new feature" flag/field exists but never does anything on the frontend | The access-control method (e.g. `can_access_from_current_website`) still reads the *old* single-value field a mixin defines, while the app only ever populates the *new* multi-value field it added | Override the access method to check the new field |
| A `NameError` buried in an `except` clause that never seems to fire in normal use | Exception class referenced without being imported — only surfaces under the exact race condition the `except` exists to handle | Add the import; also check except-clause order (specific subclasses before their parent, e.g. `OperationalError` before `Error`, or the parent swallows everything first) |
| A modern lint suggestion breaks at runtime on an old branch | The suggested API was added in a *later* Odoo version than the branch targets | Verify the suggestion against the actual target version's core before applying; if inapplicable, revert with a justified, scoped disable comment |
| `.pyc`/`__pycache__` show up in a diff | The repo's `.gitignore` doesn't cover them (or only covers them going forward) | Add the standard ignore section, `git rm --cached` anything already tracked, and say so explicitly in the PR — it's a removal, not new junk |
| CI step fails with `pip: not found` (or similar) inside a vendor Docker image | The image only exposes `python3 -m pip`, not a bare `pip` executable | Invoke via `python3 -m pip` / `python3 -m coverage` instead of the bare command |
| A test passes locally but not in CI (or vice versa) with an identical assertion | Environment mismatch invisible from the assertion itself — e.g. a different demo dataset shape, a public/portal user lacking read access to a record the test created without publishing it (`website_published`), or a route requiring a parameter your test omitted | Reproduce the *exact* failing request/record state, don't just re-read the assertion; check auth/access rules and required params first |
| A feature that used to work is now dead with zero errors anywhere — no exception, no console error, condition just never true | Core didn't rename the field/mechanism the app's condition depends on, it *replaced* it with a differently-shaped one (e.g. a 3-value select field replaced by a boolean plus a separately-computed float, or a `virtual_available`-style field dropped from the data payload entirely) — the old field name is simply absent from the new context, so the check is unconditionally false | Diff the *actual* new fields/shape in the target version's core (the model, and what the equivalent core template/JS now reads) against what the app's condition assumes; redesign the condition around the new shape, don't just search-and-replace the field name |
| An element renders once (confirmed via a direct render call or a log) and then is gone from the live DOM a moment later, no error anywhere | It shares a CSS class/id naming convention with something core's *own* JS explicitly searches for and removes as part of its own re-render/cleanup cycle (e.g. `$(...).find('.some_prefix_' + id).remove()` before injecting a fresh message) — the app's element matches that selector and gets swept up in the same cleanup, especially likely if the app's original author copied the naming convention from core in the first place | Grep the target core's JS for `.remove()`/`.empty()` calls near the class prefix in question; rename the app's element to a prefix core never searches for |
| A "native" core event/hook that used to carry the data you need now fires only sometimes, or never, depending on unrelated settings | The core JS that dispatches it is gated behind a *different* feature's config field (e.g. a native "Google Analytics" integration setting, unrelated to the app's own similarly-named key) — sites that don't have that other feature configured never get the trigger, even though the app's own settings are correct | Trace back to *where* core actually dispatches the event/sets the data, not just where it's consumed; if the underlying data is computed unconditionally elsewhere (a data attribute rendered server-side regardless of the gate) read that directly instead of depending on the gated trigger |
| JS still looks like it did on the original version, several migrations later | Each version's migration ported the frontend code forward unchanged because "it still works" — nobody checked what the target version's own core had already moved to | Per SKILL.md, Migration Strategy: match whatever pattern the target version's own core uses for the same kind of surface (`publicWidget`/OWL, ES6 `@odoo-module`, vanilla JS over jQuery where core's equivalent already made that switch) |
| An xpath targeting a `class` attribute stops matching after a version bump, with no other change to that element | Core rewrote the template to use `t-attf-class`/`t-att-class` instead of a literal `class` — Odoo's `hasclass()` xpath helper (`ir_ui_view.py`) only ever reads the literal `class` attribute, never a dynamic one | Match on `contains(@t-attf-class, '...')` (or the relevant dynamic attribute) instead of `hasclass()` |
| A widget's whole JS file throws at module-load time (`.include()` on `undefined`), and the feature it adds silently never appears anywhere | Core replaced a legacy `publicWidget.registry.*` entry this app extended with a new Interaction class (`@web/public/interaction` + a specific module's `interactions/*.js`) — the old registry entry simply doesn't exist anymore | Rewrite the extension using `patch()` (`@web/core/utils/patch`) on the Interaction class's prototype, chaining through `super.<method>(...)`, matching the pattern the target version's own core modules use for the same class of widget |
| A core event handler (`add_to_cart_event`, `view_item_event`, etc.) that used to carry extra data now fires but the data is missing, with zero console errors | Core switched from jQuery's `$el.trigger(name, [extraArgs])` to a native `element.dispatchEvent(new CustomEvent(name, {detail}))` — jQuery still delegates native custom events to `publicWidget`'s events map, but the payload no longer arrives as extra positional arguments (`Array.prototype.slice.call(arguments, 1)` returns empty) | Read `ev.originalEvent.detail` instead of extra handler arguments |
| Combining a domain built with `expression.AND()`/`OR()` and a domain from an overridden core method now crashes with something like `unsupported operand type(s) for &: 'DomainAnd' and 'list'` | Core replaced the old list/tuple domain representation with a `Domain` AST class (`odoo.fields.Domain`) — the overridden method's `super()` call now returns a real `Domain` object, not a plain list, and `expression.AND()` doesn't know how to combine the two | Wrap the app's own domain in `Domain(...)` (accepts old-style `'\|'`-prefixed tuple syntax) and combine with `&`/`\|` operators instead of `expression.AND()`/`OR()` |
| A route that used to render fine now 404s or redirects unexpectedly for a scenario that looks unrelated to what actually changed this version | A new `ir.rule` added this version hides records with a specific empty/unpublished state from public or portal users entirely (e.g. a category with zero published products) — the route's own logic (auth gate, redirect, etc.) never even gets reached because the record lookup itself fails access first | Reproduce with a record that actually satisfies the new rule (e.g. give the test category a real published product) to isolate the scenario actually being tested from the new access restriction |
| A module's Apps Store listing page (`static/description/index.html`) still shows a Settings screen, button, or field from several versions ago | Nothing in the automated pipeline touches this file — it's marketing HTML with static screenshots, invisible to tests, lint, and coverage alike | Per SKILL.md, Migration Strategy: once a version's real UI changes are known, check every screenshot against the current UI and regenerate any that have drifted |
| A field/button only shows on some records; on confirmed/sent/done ones it's just absent, forever, with no errors | The field is populated imperatively by several mechanisms that drifted apart (an onchange + a `create()` override + an install-hook backfill whose raw SQL filters by `state`) — records outside the covered states never get the value and nothing ever recomputes it | Convert to a real computed field (`compute=`, `store=True`, `@api.depends(...)`) and delete the imperative writers; confirm via the consumer (JS/view) what the *actual* dependencies are before writing the `@api.depends` |
| After converting an existing plain field to `compute=` + `store=True`, old rows stay NULL after upgrading — only new records compute | Odoo's `_auto_init()` only auto-recomputes a stored compute field when its DB *column is newly created* (`Field.update_db()` returns `not column`); a column that already existed (it was a plain field before) is skipped entirely | Keep/rewrite an explicit `post_init` hook (and an upgrade `migrations/` script for existing installs) that calls the real compute method on all rows — no state filters — plus an explicit `flush_recordset()`/`flush()`: the compute alone only fills the ORM cache, and same-transaction raw-SQL reads won't see it |
| A module's documented central behavior silently no-ops from some version on — installs green, tests green, does nothing | Core *replaced the mechanism* the module's condition reads without renaming anything: e.g. the UI action that used to write a DB column (company switcher writing `res.users.company_id` pre-13.0) became session/context-only, so raw-SQL reads of that column no longer reflect what the user selected | Trace what the *target version's* UI action actually writes/reads (grep the switcher/action's own JS+controller in core) and re-anchor the module on that; if it can't be honestly re-anchored yet, `installable: False` with a dated comment (see SKILL.md, Migration Strategy) beats shipping it dead |
| Inline `<script>`/`onclick=` inside popover/tooltip HTML content does nothing from some version on, silently | Bootstrap ≥ 4.3's sanitizer strips script tags and `on*` attributes from popover/tooltip content before injection — no error, the handlers are just gone | Move behavior out of the HTML string into real delegated JS handlers bound after render (`shown.bs.popover` etc.); never ship logic inside popover content markup |
| An overlay (popover/tooltip/dropdown) survives navigating to another record and floats over the wrong screen | The overlay element is appended to `<body>`, so destroying the widget that created it doesn't remove it; nothing else owns it | Dispose the overlay in the widget's `destroy()` and register any document-level (outside-click) handlers with a per-instance event namespace so they're removable |
| Clicking an expand/toggle briefly opens then instantly closes (or handlers seem to run twice) | The same delegated handler got bound from more than one lifecycle callback (e.g. `shown.bs.popover` *and* an RPC-refresh `.then()`), and again on every reopen — one click runs the toggle N times | Make handler-binding idempotent: namespaced events, `.off('click.ns')` before `.on('click.ns', ...)` — always, in any `_bind*Handlers`-style helper |
| A popover/modal table stretches across the whole screen with huge dead gaps between columns | Bootstrap's `.table` class forces `width: 100%`, and the overlay container itself has no width constraint — so column widths are distributed over all available space | Content-size it: `table { width: auto }`, `white-space: nowrap` cells, right-aligned numeric columns with a small `min-width`, and a sane `max-width` on the overlay container |
| A PR that was fine reports conflicts later (or from the start) even though "nothing touched the base" | The version target branch was cut from a commit that is *not an ancestor* of the work branch (e.g. from a sibling branch's later tip), so both sides carry different versions of the same files | Always cut the target branch at the merge-base with the work branch; if already diverged and the work branch's tree is the complete intended state, `git merge -s ours <base>` on the head (documenting why in the merge commit) resolves it without risking content |
