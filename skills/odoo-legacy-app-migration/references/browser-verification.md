# Real Browser Verification

Expansion of Verification Ladder step 5 in SKILL.md: the traps a green
tour run hides, and when to reach for Playwright instead.

- **The headless Chrome console a tour runs in is not a black box — read it.** Odoo pipes every `console.log`/`warn`/`error` call made during the tour into the test log itself, through a `<test>.browser` child logger (`ChromeBrowser._handle_console` in `odoo/tests/common.py`) — grep the *full* test log for it, not just the pass/fail summary line, the same way this skill already insists on reading logs instead of trusting exit codes elsewhere. A single `console.error` auto-fails the test *and* auto-saves a screenshot before doing so.
- **Pass `--screenshots <dir>`** so you know exactly where that failure screenshot lands (Odoo saves one automatically either way, into a temp dir if you don't), and **actually open the PNG** — don't infer what broke from the exception text alone.
- **Pass `--screencasts <dir>`** for a literal "watch it with your own eyes" artifact: Odoo records a real video of *every* `start_tour()` run, pass or fail, to `<dir>/<db_name>/screencasts/` — play it back for the specific interaction you're verifying instead of trusting a green result.
- **Keep a standalone Playwright (or equivalent) pass as the fallback**, for checks a tour's own step/assertion model genuinely can't reach — inspecting a third-party JS payload (e.g. intercepting a `dataLayer.push` call before a page navigates away), multi-tab/multi-window scenarios, or anything needing to observe raw network traffic.
- **Zero console errors is not the same as "the feature works," in a tour or in Playwright.** A UI element that silently fails to render (a missing condition, a class collision with something else on the page, a field that no longer exists) throws *no* JS error at all — it's just absent. A tour step that "completes" because its target selector silently matches nothing is the tour-framework version of this same trap. For every feature under test, explicitly assert the thing is *present* (the button exists, the modal opens, the expected text shows), not only that nothing crashed.
- **A blocked or empty result from a click can mean the test raced a real page transition, not that the code is broken.** Add-to-cart/remove-from-cart flows sometimes do a full page reload on older Odoo versions and pure AJAX on newer ones (this differs *between* target versions, not just between apps) — if you read page/JS state right after a click and get nothing, check whether a navigation happened before concluding the handler never fired; prevent the navigation (block the request, stub `form.submit`, or add a synchronous `preventDefault` listener) and retry before calling it a bug.
- **Exercise the flow on records in every relevant business state, not just freshly-created drafts.** Imperative data-population bugs (a backfill/onchange that only covers `state='draft'`) are invisible on the draft records a quick test creates and only surface on confirmed/sent/done ones — precisely the records real users look at. Open at least one confirmed/completed record per documented surface.
- **Interact PAST the first render: expand/collapse, close via outside click, then navigate to a different record and look back.** Overlay widgets (popovers/tooltips/dropdowns) attached to `<body>` outlive the widget that created them; double-bound handlers make toggles undo themselves instantly; none of this shows up in a "button renders, popover opens" smoke check.
